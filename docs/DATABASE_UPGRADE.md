# Safe PostgreSQL runtime upgrade

New installations generated by `scripts/setup.py` select
`FOXORY_DATABASE_LAYOUT=modern`. The Community image uses pinned PostgreSQL17
Alpine inputs and a small signed su-exec helper. Legacy PostgreSQL17 Bookworm and
its old helper had blocking scan findings. The legacy build target remains an
explicit temporary maintenance/rollback option, not an accepted release layout.

**Existing .env files are never edited by setup.** Missing layout selection stops
Compose configuration before services are changed. Do not set modern and attach
your old physical database volume: libc/musl collation/OS compatibility is not a
physical-upgrade guarantee. The modern entrypoint refuses old, partial, wrong-
major or unknown directories before the upstream process can chmod/chown them.
Fresh clusters receive a private layout marker after initdb. The marker is a
compatibility guard, not protection against an administrator forging it.

The supported transition is a consistent logical dump into a **new volume**.
The following is an owner maintenance procedure, not an automatic script. Read it
completely. Do not run it on unrelated installations or remove volumes.

1. Keep the original .env private and preserve original Compose configuration and
   exact images. Record project/container/volume names and versions. Stop app
   writes for a consistent application+document backup. Back up application data,
   documents and manager state separately; `scripts/backup.py` covers native
   SQLite only. Test restoration of those backups.
2. Create a private logical dump using the existing services. Default DB/role are
   `foxory`; adjust only after reviewing the actual installation:

   ```bash
   umask 077
   mkdir -p "$HOME/foxory-upgrade-backup"
   FOXORY_DATABASE_LAYOUT=legacy docker compose exec -T db \
     pg_dump -U foxory -d foxory -Fc > "$HOME/foxory-upgrade-backup/database.dump"
   test -s "$HOME/foxory-upgrade-backup/database.dump"
   sha256sum "$HOME/foxory-upgrade-backup/database.dump"
   db_id="$(FOXORY_DATABASE_LAYOUT=legacy docker compose ps -q db)"
   docker inspect "$db_id" --format '{{range .Mounts}}{{if eq .Destination "/var/lib/postgresql/data"}}{{.Name}}{{end}}{{end}}'
   ```

   The inspection records the original volume; never print `Config.Env`, which
   contains secrets. Preserve this volume. Review custom roles/extensions and
   locale-dependent indexes before choosing an Alpine target.
3. Rehearse first on disposable data. The compatibility test checks separate
   source/target volumes, revision0003, account hashes, memberships/sessions,
   consumed approvals, tenant boundaries and unchanged legacy bytes/ownership
   after refused physical reuse. This is not validation of every owner dataset.
   Restore only trusted owner dumps; SQL dumps can contain executable SQL.
4. For the reviewed transition, set the private layout to modern and set
   `FOXORY_LEGACY_DB_VOLUME` to the inspected original name. Select the upgrade
   override, which mounts a NEW `postgres_v2` volume and marks the original
   external. Start only db during restoration; keep app writes stopped:

   ```bash
   docker compose -f compose.yaml -f compose.database-upgrade.yaml config --quiet
   docker compose -f compose.yaml -f compose.database-upgrade.yaml build db
   docker compose -f compose.yaml -f compose.database-upgrade.yaml up -d --no-deps db
   ```

   Wait until db is healthy. The initialized target must be a NEW empty
   application database. Restore with errors enforced:

   ```bash
   docker compose -f compose.yaml -f compose.database-upgrade.yaml exec -T db \
     pg_restore --exit-on-error -U foxory -d foxory < "$HOME/foxory-upgrade-backup/database.dump"
   ```

5. Verify revision, login, membership, approvals, records, references, original
   documents and locale/index behavior. Start app using the SAME override only
   after acceptance. The matching source app/file backup is required; a DB dump
   alone is not a full app restore. Keep original volume/backup for rollback.
   Never use `down --volumes` during migration. Retain this override permanently
   for this installation; omitting it selects the original, guarded volume.

On failure stop writes and preserve both volumes. Do not delete markers or chown
the original to force startup. Roll back with saved original images/config and
the original volume; post-cutover writes need separate logical reconciliation.
Repository updates and test workflows do not perform owner cutover.
